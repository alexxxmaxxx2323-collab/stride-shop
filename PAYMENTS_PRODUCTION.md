# Платежи ЮKassa — готовность к бою (production checklist)

Что уже сделано и проверено на песочнице, и что обязательно закрыть **перед приёмом
реальных оплат**. Песочница проверяет логику интеграции 1:1, но НЕ покрывает
фискализацию, реальные карты и нагрузку.

## ✅ Проверено на песочнице (2026-06-01, заказы #83/#84)
- Создание платежа → встроенный виджет → `complete` → серверная сверка `/check`.
- Сведение статуса в `paid`, начисление кэшбэка (идемпотентно), уведомления (ЛК + бот + почта).
- Webhook `payment.succeeded` (перезапрашивает платёж у ЮKassa, не доверяет телу).
- Тот же SDK/API/статусы, что и в бою — отличие только `test_` vs `live_` ключ.

## ❗ Обязательно перед боевым запуском

### 1. Чеки 54-ФЗ (фискализация)
- Для продаж физлицам в РФ онлайн-чек **обязателен по закону**.
- В песочнице не проверяется. Передавать объект `receipt` при создании платежа
  (позиции, НДС, контакт покупателя), подключить онлайн-кассу/ОФД в ЛК ЮKassa.
- **Статус: НЕ сделано.**

### 2. Webhook на проде (а не только клиентский `/check`)
- Если клиент закроет вкладку / потеряет сеть сразу после оплаты — `/check` не
  вызовется, заказ зависнет в `awaiting`. Webhook — обязательная страховка.
- В ЛК ЮKassa: уведомление `payment.succeeded` → `https://<домен>/payments/yookassa/webhook`.
- Желательно проверять подпись/источник webhook (сейчас доверяем только перезапросу платежа — это ок, но IP-allowlist лишним не будет).
- **Статус: код есть, на проде не настроен/не проверен.**

### 3. Реальный платёж + отказ
- Один живой платёж на минимальную сумму (карта/СБП) + возврат через ЛК.
- Проверить отказную карту и реальный 3-D Secure.
- **Статус: НЕ сделано (ждёт активации боевого магазина).**

## ⚙️ Инфраструктура под нагрузку (несколько клиентов одновременно)

Узкое место — **наша сторона, не ЮKassa.** Для демо-портфолио текущего хватает,
для реального потока заказов — закрыть до запуска:

### 4. SQLite → PostgreSQL
- `shop.db` пишет с блокировкой на всю БД → при параллельных оплатах `database is locked`.
- Перевести `DATABASE_URL` на Postgres, прогнать alembic-миграции, проверить пул соединений.
- **Статус: SQLite (ок для демо, НЕ для боевого потока).**

### 5. Несколько воркеров / async
- Сейчас 1 процесс uvicorn; платёжные эндпоинты синхронные → блокирующие вызовы
  к API ЮKassa занимают потоки threadpool, под нагрузкой очередь.
- Прод: `uvicorn --workers N` (или gunicorn+uvicorn worker) за nginx; рассмотреть
  перевод платёжных вызовов на async-HTTP.

### 6. Гонка идемпотентности кэшбэка
- Если webhook и `/check` прилетят одновременно по одному заказу — есть TOCTOU-окно:
  оба пройдут проверку `payment_status != paid` до коммита друг друга → двойной кэшбэк.
- На SQLite сериализация записи частично прикрывает; на Postgres — добавить
  `SELECT … FOR UPDATE` на заказе при сведении ИЛИ уникальный constraint на
  бонус-транзакцию кэшбэка (`order_id` + тип = «Кэшбэк»).
- **Статус: идемпотентность есть на уровне приложения, гонку под параллелью не закрыли.**

## Базовый «боевой» стек для будущих проектов (как делать сразу правильно)
- БД: PostgreSQL с самого начала (а SQLite — только для локальной разработки/демо).
- Запуск: gunicorn/uvicorn с несколькими воркерами за nginx, HTTPS (certbot).
- Платёжные/сетевые вызовы — async, с таймаутами и ретраями.
- Идемпотентность подтверждать на уровне БД (constraint/row-lock), а не только проверкой в коде.
- Webhook обязателен; клиентский поллинг — только как UX-ускорение.
- Фискализация (чеки) заложить в модель платежа сразу, если продажи физлицам в РФ.
